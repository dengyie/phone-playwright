# Phone-Playwright: 面向 AI Agent 的移动端语义交互引擎

## 1. 项目愿景与设计哲学

### 1.1 背景与核心痛点
在桌面浏览器领域，Playwright 赋予了 AI 两个决定性的能力：
1. **语义化感知**：通过精简的 Accessibility Tree（AXTree）让大模型“看懂”页面，避免全图视觉推断的高延迟与高成本。
2. **确定性交互**：通过 `Locator` 与 `Auto-waiting` 机制，保障在动态异步渲染、动画过渡期间操作的极高成功率。

而在移动端（Android / iOS），现存生态存在严重断层：
- **原生无障碍树不能直接给 AI 用**：原生的 UIAutomator / XCTest 层次树深达 20~30 层，体积 30KB~80KB，充斥大量无用布局容器，更致命的是包含**大量视口外（Off-screen）元素**，导致 AI 产生严重的点击幻觉与死循环。
- **纯视觉多模态（VLM）方案昂贵且不稳定**：截全屏送大模型耗费大量 Token，推理延迟在 2~4 秒以上，且存在坐标漂移、动态刷新时状态丢失问题。
- **跨平台方案重型笨拙**：Appium 协议繁重通信缓慢；Mobilewright 等工具偏向人工回归测试，缺乏面向大模型交互的剪枝和容错层。

### 1.2 本项目定位
**Phone-Playwright 是一个专为 AI Agent 打造的、轻量级移动端语义感知与自动化交互引擎。**
- 它**不重新制造底层的通信轮子**（在 Android 上复用成熟的 ADB / UIAutomator RPC 通道，在 iOS 上复用 WebDriverAgent 通道）。
- 它的核心聚焦于两点：
  1. **面向 LLM 的视口剪枝与语义蒸馏（Viewport-Aware Semantic Pruning）**：把 50KB 的噪声树压缩成 1KB 的高确定性交互清单，杜绝屏幕外幻觉。
  2. **Playwright 风格的动作可用性状态机（Actionability & Auto-waiting Engine）**：提供 `locator().click()`、`locator().fill()`，内部封装元素可见性检测、动画稳定判定、焦点注入与自动重试。

## 3. 分层模块职责划分

### 3.1 核心抽象层 (Abstraction Layer)
- **`PhoneDevice`**：代表一台手机的抽象会话，持有生命周期、当前页面实例。
- **`PhonePage`**：代表当前手机激活屏幕，提供 `snapshot()`、`locator()`、`screenshot()` 等操作。
- **`PhoneLocator`**：Playwright 风格的延迟定位器，持有选择器策略（Ref ID、Text、Role、ID），每次执行动作前动态解析。

### 3.2 语义感知引擎 (Semantic Perception Engine)
- 负责获取当前活跃窗口的物理像素尺寸 $(W, H)$。
- 递归解析底层驱动产出的原始无障碍树。
- 执行几何视口裁剪（Viewport Clip）、冗余节点收缩（Node Collapse）与文本合并。
- 产出紧凑的 `CompactAXTree`，附带可交互标记（`@1, @2, ...`）。

### 3.3 交互执行引擎 (Action Engine)
- 实施 Playwright 核心规范中的 **Actionability Checks**：
  1. `Attached`：元素节点在当前树中存在。
  2. `Visible`：元素外接矩形与屏幕视口交集面积大于 0。
  3. `Stable`：在连续两个采样周期（如 150ms 间隔）内，元素外接矩形坐标漂移量 $< \epsilon$（判定页面停止滚动或动画结束）。
  4. `Enabled`：元素未处于禁用状态。
- 计算物理安全点击区域（默认中心点，若遇异形则偏移）。
- 下发驱动层 Tap / KeyInput / Swipe 操作。

### 3.4 设备舰队管理器 (Fleet Manager)
- 自动扫描局域网 mDNS 广播（如 Android 11+ 的无线调试配对）。
- 维持设备心跳，解决移动设备熄屏降频、Wi-Fi 调试链路休眠导致的断连问题。
- 提供命名设备池（`fleet.get("device-a")`）。
